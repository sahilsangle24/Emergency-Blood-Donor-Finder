# Development Stages 3–5 — Implementation and Verification Status

This package continues the latest Development Stage 2 ZIP. It contains source/configuration changes, not a claim of local Oracle/Tomcat certification.

## Stage 3 — Integration and deployment readiness

- Changed the Axios API default to a same-origin `/api` base.
- Added a Vite development proxy to Tomcat, configurable with `EBDF_TOMCAT_ORIGIN` and `EBDF_TOMCAT_CONTEXT`; rewrites the Tomcat JSESSIONID cookie path so the session cookie is sent on Vite `/api` calls.
- Added a production Vite build target under `src/main/webapp/app`, allowing the React frontend and Java servlets to ship in one WAR.
- Added React Router production basename handling and an extensionless-path SPA forwarding filter for Tomcat.
- Added explicit Maven compiler and WAR plugin versions for Java 21 / Tomcat 9.
- Removed a machine-specific Eclipse classpath reference; Maven supplies Servlet, Gson, BCrypt and Oracle JDBC dependencies.
- Added Windows PowerShell and CMD build/package scripts.
- Added `/api/health` to test Oracle connectivity without exposing credentials or exception details.

## Stage 4 — Oracle installation and migration

- Added `database/00_install_or_upgrade.sql`: creates missing tables in dependency order, preserves existing tables/data, seeds blood groups and compatibility pairs idempotently, adds missing settings and indexes, then runs schema verification.
- Added `database/00_create_app_user.sql` for optional one-time creation of `EBDF_APP` from the `FREEPDB1` PDB as SYS.
- Reworked `database/02_stage2_migration.sql` to create `DONOR_INVITATIONS` only when absent and add its indexes safely.
- Added `database/03_verify_installation.sql` to validate all required tables/columns and the 8 blood groups / 27 compatibility pairs.
- Added `database/04_promote_admin.sql` to promote one existing account without requiring the user to write SQL manually.
- Oracle identity columns provide their own backing sequences; separate user-managed sequences are not needed by this schema.

## Stage 5 — Security, validation and workflow hardening

- Restricted CORS to an explicit origin allow-list; wildcard credentialed CORS is not used.
- Added response security headers, HTTP-only session cookie configuration, cookie-only session tracking, 30-minute session timeout and SameSite=Lax Tomcat cookie configuration.
- Kept public registration limited to DONOR and REQUESTER roles.
- Added a session security filter that rechecks account status and role against Oracle on protected API requests, invalidating sessions for deactivated accounts.
- Added server-side validation for donor availability/consent and future dates, request units/required-by/hospital fields, donation units/date/hospital, and administrator settings.
- When a donation record references a request, the DAO now verifies that the logged-in donor has an accepted response for that request before inserting the record.
- Restricted donor access to request details to compatible requests that are currently available to that donor or to requests for which they have an invitation/response.
- Donor-facing request details no longer include free-text request details; older records could contain patient-identifying information in that field. New request submission no longer sends patient name as free text and displays a privacy warning.
- Retained non-destructive admin account/request status changes to preserve foreign-key history.

## Remaining local verification steps

1. Execute `database/00_install_or_upgrade.sql` as `EBDF_APP` in `FREEPDB1` and share the full SQL*Plus output.
2. Run `build-and-package.ps1` from Windows and share any `npm`, ESLint, Vite or Maven errors.
3. Deploy `target/EmergencyBloodDonorFinder.war` to Tomcat 9, set the `EBDF_DB_*` environment variables before starting Tomcat, and open `/EmergencyBloodDonorFinder/`.
4. Check `/EmergencyBloodDonorFinder/api/health`; it should return HTTP 200 and `database: connected`.
5. Exercise registration/login, donor profile, request creation, donor accept/reject, requester tracking/cancellation, notifications, donation submission/admin verification, and admin status/settings actions.

## Known scope limits

- Email/SMS/push delivery is not configured; notifications are stored in Oracle and displayed in-app.
- Live WebSocket updates are not implemented.
- No automated medical eligibility decision, distance routing, or transfusion authorization is claimed. Hospital staff must verify compatibility and eligibility.
- Admin record removal is implemented as status changes rather than irreversible deletion.
